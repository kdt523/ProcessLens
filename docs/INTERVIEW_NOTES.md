## Prepared questions

### 1. Why PR-AUC and not accuracy or ROC-AUC on a 6.6% base rate?

Accuracy rewards predicting 'pass' for everything (6.6% failures). ROC-AUC is dominated by the many easy negatives and looks flattering. PR-AUC measures how clean the top of the ranking is, which is what an inspection team pays for, and its no-skill level is the base rate: I report 0.099 next to 0.054.

### 2. Why a time-ordered split? How did you prove there's no leakage?

The failure rate moves from 8.1% / 3.5% / 5.4% across train / validation / test, and sensors drift (see the PSI report), so a random split would let the model learn the future. Proof is in `tests/test_leakage.py`: strict timestamp order with no ties broken, imputer/scaler statistics equal to train-only statistics, corrupting test rows changes nothing that was fitted, a column that is all-missing in train is dropped even if test has values, and no feature can be the label or the timestamp.

### 3. Your PR-AUC is modest. Why is the project still useful?

Because I report it honestly: random forest is not significantly better than logistic regression (paired bootstrap +0.009, CI -0.060 to +0.125). The ranking still catches 41% of failures in the riskiest 20% of runs, roughly double random inspection. And the core contribution is the root-cause engine plus a benchmark that measures when it can and cannot be trusted.

### 4. How do you handle hundreds of highly correlated sensors? Why clusters?

I cluster on 1 − |Spearman ρ| (444 sensors → 237 clusters at ρ ≥ 0.8) and report suspects per cluster. Within a cluster the data cannot say which sensor matters; the benchmark shows this: the consensus ranks the planted cluster in the top 5 in 62% of scenarios but the exact sensor only 54%.

### 5. Can this prove causality?

No. It is observational data; rankings are suspects associated with failure. The verifier even rejects causal phrasing in copilot reports. Confirmation needs process knowledge or a controlled trial; the recommended checks are designed for that.

### 6. How realistic is the planted-fault benchmark, and where could it mislead?

It keeps the real sensor matrix, so missingness, correlation and drift are real; only the labels are synthetic. It can mislead because planted effects are additive and clean: no interactions, lags, label noise or unmeasured causes. So its numbers are an upper bound. It already shows real weaknesses: minimum detectable effects are drift_window not reached, linear β = 1, threshold β = 1, and the consensus did not beat the univariate screen (62% vs 64% cluster hit@5), which I report rather than tune away.

### 7. Why doesn't the LLM pick the root cause? How do you stop it inventing numbers?

The statistics decide; the LLM explains. It only sees typed tool summaries, never raw rows. The abstain branch is decided in code from evidence grades. Every number in the report must cite a tool call and match its output (rounding-aware); free-text numbers must appear in the log; evidence grades cannot be upgraded; failures go back to a revise node at most twice. Tests include a deliberately wrong number that must be caught.

### 8. What would change in a real Michelin plant?

Data volume and streaming (historian feeds, incremental drift checks), per-line or per-recipe windows, sensor metadata so clusters get physical names, engineers in the loop to label investigation outcomes, and a benchmark recalibrated on the plant's own data. The guardrails stay: contracts, leakage tests, measured limits, verified reports.
